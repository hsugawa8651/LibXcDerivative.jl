Public methods

The package exports 2659 names, of which 52 are hand-written. The list below is that hand-written surface; the functionals themselves are described by their naming rule rather than enumerated.

The generated names are not a fixed number per functional, and the shape is worth knowing before reading the rule:

nameshow manywhat they are
<name>715an entry point under a functional's own name
<name>_vxc8an entry point returning a potential (group 8)
<name>_defaults, <name>_required732 eachone pair per entry point
<name>_energy279a kernel, fewer than the entry points because several registered names share one
<name>_potential4the potential-only kernels
<name>_components154the recipe of a functional Libxc evaluates as a weighted sum

The 732 entry points cover Libxc's 697 identifiers, plus 35 kernels Libxc does not register under a name of their own but which are callable here anyway.

The grouping follows Libxc's own division of its C API where there is one, with one group added: Libxc's kernels call mathematical helpers that xc.h does not declare, and this package exports them because its kernels call them too.

1. The functionals themselves

Not listed here, there being 697 of them. Each identifier gives at least three exported names, and a fourth if it has a kernel of its own:

namewhat it is
gga_x_pbethe entry point: density in, zk out, params keyword
gga_x_pbe_defaultsthe thresholds and constants Libxc uses, a NamedTuple
gga_x_pbe_requiredwhat has no default and must be supplied
gga_x_pbe_energythe kernel: reduced variables and every parameter, positional

Only 245 of the 697 have a <name>_energy of their own. The rest reach a kernel registered under another name: gga_x_xpbe and gga_x_t_pbe2 both call gga_x_pbe_energy with different parameter values, so gga_x_xpbe_energy does not exist. A functional Libxc evaluates as a weighted sum has a <name>_components instead of a kernel.

Seven identifiers that return a potential instead carry a _vxc suffix on the entry point (group 8). available_identifiers lists every identifier; Calling a functional explains the names.

2. Evaluation and derivatives

LibXcDerivative.xc_exc_vxc — Function
xc_exc_vxc(f, rho)
xc_exc_vxc(f, rho, sigma)
xc_exc_vxc(f, rho, sigma, lapl, tau)
xc_exc_vxc(f, (na, nb))
xc_exc_vxc(f, (na, nb), (gaa, gab, gbb))
xc_exc_vxc(f, (na, nb), (gaa, gab, gbb), (la, lb), (ta, tb))

Return the energy per particle of f and its first derivatives, named.

The density is given as a total or as its two spin channels, and the result is a NamedTuple: zk for the energy per particle, then one field per derivative. The names are Libxc's, so code ported from it reads the same quantity out of the same field.

Why this exists. Everything else here returns one scalar and leaves the derivatives to the caller's ForwardDiff, which is the whole design: Libxc's own interface fills arrays from C and cannot be differentiated through at all (evaluate! takes Float64 arrays, and a Dual is a MethodError). But it leaves one convention in the caller's hands, and it is easy to get wrong:

  • vrho is the derivative of rho * zk, not of zk
  • vsigma, vlapl and vtau are rho times the derivative of zk

Named slots state that once. The result is a NamedTuple with the fields Libxc fills for the family, so a caller reading s.vsigma is reading the quantity xc_gga_exc_vxc would have put in vsigma.

All of them come out of one forward pass over the expression, seeded in every argument at once. Where that pass returns anything that is not finite it is discarded and the slots are taken from one chain per argument instead, which is slower and is what a zero of sigma does, and a zero of tau with it, since Libxc's clamp takes sigma to zero there. The Limits page says which slots are finite at those points and which are not.

Type-stable: the field set is fixed per method, so there is no order to pass and nothing to infer. Over a grid, xc_exc_vxc.(f, rho, sigma) gives an array of these with a concrete element type; a caller who wants columns instead writes (; vrho = getfield.(v, :vrho), vsigma = getfield.(v, :vsigma)).

Cost, re-measured on 2026-10-24 on gga_x_pbe at 50000 points, every slot consumed, with the loop in a top-level function: 70 ns a point, the same whether the functional is named in the loop or passed to it as an argument, since Julia specializes on its type. Read from an untyped global inside the loop instead it cost 990 ns and allocated 496 bytes a point, so what a loop needs is not a fixed functional but one whose type the compiler can see. Writing the two derivatives out by hand, as two seeded passes, came to 124 ns: slower than asking for all of them at once, which is the point of the one pass, though what a hand-written pair costs depends on how it is written.

Nothing is allocated, in a top-level function or inside a @testset, and the suite asserts that rather than any of these times, which belong to the machine they were taken on. The slots have to be assembled in a method the compiler will inline into the caller's loop: where they are not, the entry point allocates on every point, 755 ns and 384 bytes a point on the GGA path. test/derivatives.jl pins it at zero bytes.

A functional that reads tau carries the input clamp libxc_clamp describes as well, which asks a table on every point. Measured on 2026-10-24 in the same shape of loop, the functional arrives there as a type parameter and the table is indexed rather than defaulted, which costs 9 ns and nothing: mgga_x_scan reads 387 ns a point against 352 with enforce_fhc=false. Passed instead as an argument the clamp never calls, it costs 88 ns and 32 bytes a point, since Julia compiles one instance covering every functional rather than one each, so the name is looked up at run time and the lookup's union-typed result is boxed.

The scope of the loop matters more than it should and is worth saying. The figures above are all from a loop in a function, with the inputs in arrays. Written in a let block rather than a function the same loop times slower, a loop handed literal arguments is folded away before it runs, and a loop that reads its functional from an untyped global pays the 990 ns above. A sweep driven from inside a @testset reads zero as well: what makes a reading of 144 bytes a point is the method not being inlined, not the scope it is measured in.

Still differentiable, unlike the interface it imitates: one more step through s.vrho is Libxc's v2rho2.

Spin-polarized densities arrive as tuples, one per quantity, and come back the same way: vrho has a component per spin, vsigma three for the (aa, ab, bb) pseudo-spin components, vlapl and vtau one per spin, which are Libxc's own widths. The convention is the one above with the total density standing where rho did, vrho[s] being the derivative of rho_total * zk with respect to rho_s, and it was read off the library rather than assumed.

Tuples rather than a flat argument list because the family is a property of f that the call site does not carry: two numbers are a GGA's (rho, sigma) and equally an LDA's (na, nb), and nothing at the call site could tell them apart.

Not for the potential-only functionals, which have no zk: they are refused by name.

The methods are in the ForwardDiff extension, so using ForwardDiff is what makes them exist. This package depends on no AD package: which one a caller differentiates with is the caller's choice, and that is the point of shipping one expression rather than a derivative implementation.

LibXcDerivative.xc_fxc — Function
xc_fxc(f, rho)
xc_fxc(f, rho, sigma)
xc_fxc(f, rho, sigma, lapl, tau)
xc_fxc(f, (na, nb))
xc_fxc(f, (na, nb), (gaa, gab, gbb))
xc_fxc(f, (na, nb), (gaa, gab, gbb), (la, lb), (ta, tb))
xc_fxc(f, slot, (na, nb), (gaa, gab, gbb), (la, lb), (ta, tb))

Return the second derivatives of f, named.

One field per independent second derivative: v2rho2 for an LDA; v2rho2, v2rhosigma, v2sigma2 for a GGA; and the ten of a meta-GGA, v2rho2, v2rhosigma, v2rholapl, v2rhotau, v2sigma2, v2sigmalapl, v2sigmatau, v2lapl2, v2lapltau, v2tau2. The names are Libxc's.

Each is a derivative of rho * zk, which is what Libxc differentiates, taken with ForwardDiff on the one expression this package ships: there is no separate second-order implementation here, as there is in Libxc, where fxc is generated C of its own.

The field set is fixed by the family, as it is for xc_exc_vxc: a meta-GGA with no Laplacian dependence gets zeros in those four slots rather than a narrower NamedTuple, which is the number Libxc would have written had it filled a slot. Libxc.jl does the opposite and leaves the fields out; the suite asserts both.

enforce_fhc=false stops the input clamp libxc_clamp describes, so that the derivatives are those of the expression this package ships rather than the ones Libxc would give. It makes no difference below the von Weizsäcker bound, which is everywhere a real density reaches.

Spin-polarized densities arrive as tuples, as they do for xc_exc_vxc, and each slot comes back with the spin axis Libxc gives it: three components for v2rho2, six for v2rhosigma and v2sigma2, four for v2rholapl and the other rho-against-two-channels slots, three for v2lapl2 and v2tau2.

The layouts are Libxc's and were read off it rather than assumed. The rule that came out: the first quantity's spin axis is outermost, and when both quantities are the same one it is the upper triangle, row major. So v2rhosigma is rho_a against (aa, ab, bb) and then rho_b against the same three, and v2sigma2 is aa aa, aa ab, aa bb, ab ab, ab bb, bb bb.

Two probes were needed. An exchange functional fixes most of the layout by its zeros, since exchange is spin-separable and every alpha-beta entry vanishes, but that leaves the vanishing positions undetermined, and comparing zero with zero establishes nothing. mgga_c_b94, a correlation functional depending on both tau and the Laplacian, has no vanishing component, and matching all ten slots there against a Hessian computed independently agreed to 1.8e-9 with nothing skipped.

A slot between the functional and the densities asks for that one slot, the form xc_kxc describes, and returns what it holds in the whole tuple. Only for a polarized density: unpolarized, the ten slots of a meta-GGA are ten numbers and the whole tuple is well under a second, so there is nothing to save.

One field per independent third derivative: v3rho3 for an LDA, four for a GGA, twenty for a meta-GGA.

xc_lxc(f, rho)
xc_lxc(f, rho, sigma)
xc_lxc(f, rho, sigma, lapl, tau)
xc_lxc(f, (na, nb), (gaa, gab, gbb), (la, lb), (ta, tb))
xc_lxc(f, slot, rho, sigma, lapl, tau)

Return the fourth derivatives of f, named: v4rho4 for an LDA, five for a GGA, thirty-five for a meta-GGA.

The names follow Libxc's rule rather than a transcribed list: for order n, the multisets of (rho, sigma, lapl, tau) in lexicographic order, each variable followed by its multiplicity where that is above one: v3rho2sigma, v3rhosigmalapl, v4rho2lapltau. The rule reproduces every v3/v4 name Libxc's libxc-upstream/src/xc.h declares, 66 of them, and the suite checks that against the header rather than against a copy of it.

Each is a derivative of rho * zk, as the lower slots are, taken with ForwardDiff on the one expression this package ships. Libxc generates C for each order instead, which is why a Libxc build fixes its highest order with MAXORDER when it is configured: here no order is compiled in advance.

Nothing to have, but not nothing to call, and the cost climbs steeply with the size of the expression. Measured on 2026-10-20: on mgga_x_scan a first call costs 4.4 s for the twenty third-order slots and 15.6 s for the thirty-five fourth-order ones. On hyb_gga_xc_hse06, which holds the 158 KiB gga_x_wpbeh kernel, the same sequence runs 0.8 s for the value, 2.7 s for the first derivative, 11.9 s for the second, 260 s for the third, and more than twelve minutes for the fourth, which was stopped rather than completed. The step from second to third is more than twenty times, not the four the first three suggest, so extrapolating from the low orders understates it badly. Repeating any of these on the same machine moves it by about a tenth: they are scale, not benchmarks.

It is paid on the first call for a given functional and order, and only if that call is made.

enforce_fhc=false stops the input clamp libxc_clamp describes, as it does for xc_fxc. Every slot function takes it, including those of an LDA and a GGA, where it has nothing to act on, so that generic code over a mixed corpus can pass it to anything.

What this means for coverage is worth stating, because it runs the other way from everything else in this package. Libxc provides a third derivative for 688 of its 702 identifiers and a fourth for 667 (hyb_gga_xc_hse06 is one that stops at second order, since gga_x_wpbeh has no third), while these answer for every functional with an energy, at each of the four orders Libxc names, because they differentiate an expression rather than call generated code. Those four are the whole surface: Libxc's own API stops at v4rho4 and so does this, and a caller who wants a fifth differentiates the expression. libxc_derivatives is what Libxc provides; it is not a limit here.

A spin-polarized density arrives as one tuple per quantity, as it does for xc_exc_vxc, and then each slot holds a tuple of components rather than a number: the thirty-five slots of a polarized meta-GGA fourth derivative hold 495 components between them. slot_widths gives the widths without evaluating anything.

xc_kxc(f, slot, args...)

One slot by name, slot being a Symbol or a Val of one of the names slot_names lists for that family and order, returning what that slot holds in the whole tuple. This is the form to call when one slot is wanted, because what costs here is the number of derivative chains compiled, one per component: the 495 components of a polarized meta-GGA fourth derivative are 51 s on a first call, and its five-component v4rho4 slot alone is under three. LibXcDerivative.slot_names — Function
slot_names(family, order) -> Tuple{Vararg{Symbol}}

Return the field names a derivative of that family and order comes back with.

Nothing is evaluated: this answers what the result of xc_exc_vxc, xc_fxc, xc_kxc or xc_lxc will be shaped like before paying for one.

family is :lda, :gga, :mgga or :mggal; order runs 1 to 4. The names are generated from Libxc's own rule, the same one the methods are generated from, so the two cannot disagree.

Asking the result instead costs an evaluation, and at high order that is not small: a third derivative of hyb_gga_xc_hse06 takes 260 s on first call. Knowing what comes back should not cost that.

source
LibXcDerivative.slot_widths — Function
slot_widths(family, order) -> Tuple{Vararg{Int}}

Return how many components each field of a spin-polarized derivative holds.

The order is the one slot_names lists the fields in, and again nothing is evaluated.

For a slot giving variable v a multiplicity k, the count is the number of multisets of v's spin channels of size k, which is C(w+k-1, k) for a channel width w, multiplied over the variables. rho, the Laplacian and tau have two channels; sigma has the three (aa, ab, bb) pseudo-spin components. So a polarized GGA third derivative is 4 + 9 + 12 + 10 = 35 components, and a meta-GGA's is 165.

The rule and the ordering were confirmed against a MAXORDER=4 build of Libxc, every component, before anything was written: Libxc.jl returns nothing above second order, so there is no other reference.

LibXcDerivative.param_gradient — Function
param_gradient(f, args...; params = NamedTuple()) -> NamedTuple

Return the derivative of f with respect to each of its own parameters, by name, at the density args and the parameter values params.

This is the derivative Libxc cannot be asked for: its generated code holds the parameters as constants read out of a struct, and the derivative tensor its generator builds runs over the density variables only. Here they are ordinary arguments, so this is the same automatic differentiation the density derivatives use.

params moves the point the derivative is taken at, not which parameters are differentiated: that is always all of param_names, and a functional with none of its own is refused rather than answered with an empty tuple. A parameter with no default has to be given a value here, since there is no point to differentiate at otherwise.

Available once ForwardDiff is loaded; the implementation is an extension, so it is not a dependency of this package.

(params_a_kappa = -1.1912752580356732e-5, params_a_mu = -0.00963510812734225)

3. Preparing the input

LibXcDerivative.libxc_clamp — Function
libxc_clamp(f, rho, sigma, lapl, tau) -> (rho, sigma, lapl, tau)
libxc_clamp(f, (na, nb), (saa, sab, sbb), (la, lb), (ta, tb))

Clamp a kernel's arguments the way Libxc does before evaluating one.

Returns the arguments it was given, except that a gradient larger than the kinetic energy density allows is cut back to that bound. For an LDA or a GGA, and for a functional this package does not ship, the arguments come back unchanged.

Libxc does not pass a caller's numbers to the kernel unchanged. For a functional that needs tau, when the Fermi hole curvature is being enforced, work_mgga_inc.c:57-80 clamps the gradient to what the kinetic energy density allows: sigma <- min(sigma, 8 rho tau), so that 1 - sigma/(8 rho tau) cannot go negative. Spin-polarized, it is done per channel (sigma_aa against 8 na ta and sigma_bb against 8 nb tb), and sigma_ab is left alone, being a cross term with no curvature of its own.

Any real density satisfies tau >= sigma/(8 rho), the von Weizsäcker bound, so the clamp does nothing to physical input and this function returns what it was given. Above the bound it is the difference between answering as Libxc does and carrying an unphysical gradient through the expression: on hyb_mgga_x_bmk at rho = 0.5, tau = 0.05 and sigma = 1.0, five times the bound, the two differ by 15 % in the energy density, and on hyb_mgga_x_cf22d by a factor of eleven.

The slot functions (xc_exc_vxc, xc_fxc, xc_kxc, xc_lxc) apply this themselves, and take enforce_fhc=false to stop them. This is here for a caller who evaluates a kernel directly, where the arguments are the caller's own and nothing is applied to them.

A functional this package does not ship has no table entry to say whether it reads tau, so its arguments come back unchanged too.

Whether Libxc enforces the curvature at all is a setting of the build, not a property of the functional: functionals.c:355 sets the flag for every functional under #ifdef XC_ENFORCE_FERMI_HOLE_CURVATURE, which CMakeLists.txt:162 leaves on. libxc_flags says more. The default here follows that build, which is the one values are compared against.

LibXcDerivative.param_point — Function
param_point(f, params = NamedTuple()) -> Vector

Return the parameter values to differentiate f at, in param_names order: params where it says, f's defaults elsewhere.

With no params this is where a fit starts from, and it is the vector params_from takes back.

Every name in params has to be one of f's own parameters. A threshold would otherwise be accepted here and then dropped by params_from, which fills the thresholds from the defaults – a caller's value discarded without a word, the failure mode resolve_params exists to prevent.

LibXcDerivative.params_from — Function
params_from(f, q) -> NamedTuple

Return the params NamedTuple that hands f the parameter values in q.

q is in param_names order and holds the functional's own parameters only; the thresholds come from f's defaults. The result is what f(args...; params = ...) wants, and is identical to the NamedTuple written out by hand – including its type, which is why it costs nothing:

julia> params_from(gga_x_pbe, [0.8040, 0.2195149727645171]) === gga_x_pbe_defaults
true

A q of the wrong length is refused. Reading past the end would be a crash and dropping the tail would be worse: a plausible number from parameters that are not the ones asked for.

Any number type goes through, duals included, which is what makes a gradient over the parameters a gradient over q.

LibXcDerivative.IdentifierFacts — Type
IdentifierFacts

What a caller has to know about a functional before calling it.

Five fields: which family it is in, whether it is exchange or correlation, which arguments it reads, and whether it has an energy at all.

None of it is parsed from the name, because the name does not carry it. mgga_x_scanl is deorbitalized SCAN and reads the Laplacian of the density instead of tau; the _x_/_c_/_xc_ segment is a convention Libxc does not enforce, and p->info->kind is what it answers from. Keyed by name, with the bound each one meets and its measured worst case in a comment beside it.

What these lose is significance in a long sum, which is why the bound here is relative where the default is absolute: an absolute bound asks least of them exactly where the value is smallest.

Where along the density that happens is not the same for all of them. The KCIS pair agrees to 1e-13 at the highest density checked and to eight digits at the lowest. LibXcDerivative.gga_variables — Function
gga_variables(rho, sigma, dim) -> (; rs, z, xt, xs0, xs1)
gga_variables(na, nb, gaa, gab, gbb, dim) -> (; rs, z, xt, xs0, xs1)

Reduce a density and its gradient to the variables a GGA kernel takes.

rs and z as for an LDA, plus the reduced gradient of the total density xt and of each spin channel (xs0, xs1), under Libxc's own names.

The two-density method takes the total density and sigma = |grad n|^2, and is the equal-spin case of the spin-resolved one, which is what fixes how sigma splits across channels: equal spins carry gaa = gab = gbb = sigma/4.

Valid arguments

rho > 0 as for LDA, and sigma >= 0, it being a squared gradient.

Spin-resolved, gaa, gbb >= 0 and the cross term is bounded by Cauchy-Schwarz, gab^2 <= gaa * gbb, since gab = grad n_a . grad n_b. That bound is not decoration: gga_c_pbe moves from -0.0696 to -0.0317 when gab is pushed from 0.1 to 10 at gaa = gbb = 0.1, and gga_c_lyp from -0.0470 to -0.0423 (2026-10-08). An exchange functional ignores gab and will not notice.

A negative sigma is not a value the quantity takes: it is a squared gradient. sqrt(sigma) here is Base's, so it throws a DomainError and says so. Libxc instead clamps it to zero and returns the sigma = 0 answer, measured at sigma = -0.1 and -1.0 on gga_x_pbe (2026-10-08), which is the defensive choice for a library handed arrays off a grid where rounding can make a squared quantity slightly negative.

That difference is not the one NaNMath is about, and the kernels' use of it is not in question here. NaNMath is for an argument that is valid and an intermediate that leaves some function's domain (the sqrt of a branch my_piecewise3 will discard) where throwing would abandon an evaluation Libxc completes. A caller passing a negative squared gradient is a different thing: there is no evaluation to complete, because the input does not describe a density. The same holds for rho < 0 above, which is answered with zero only because the threshold branch happens to catch it.

LibXcDerivative.mgga_variables — Function
mgga_variables(rho, sigma, lapl, tau, dim) -> (; rs, z, xt, xs0, xs1, u0, u1, t0, t1)
mgga_variables(na, nb, gaa, gab, gbb, la, lb, ta, tb, dim) -> (; rs, z, xt, xs0, xs1, u0, u1, t0, t1)

Reduce a density, its gradient, Laplacian and tau to a meta-GGA's variables.

The five a GGA takes, plus the reduced Laplacian (u0, u1) and reduced kinetic energy density (t0, t1) of each spin channel, under Libxc's own names.

Both of the new pairs reduce by n^(1 + 2/dim), against n^(1 + 1/dim) for the gradient, as python/libxc_codegen.py:4395-4413 forms them.

The four-density method takes the total density, sigma = |grad n|^2, the total Laplacian and the total kinetic energy density, and is the equal-spin case of the spin-resolved one. That is what fixes how the Laplacian and tau split: equal spins carry half of each, the same way sigma splits into quarters.

What tau and sigma may be

tau and sigma are not independent. Any real density satisfies

tau >= sigma / (8 * rho)

where the right-hand side is the von Weizsäcker kinetic energy density, which a single orbital attains and nothing falls below. Several meta-GGAs are built on SCAN's alpha = (tau - tau_W) / tau_unif, which is therefore non-negative for every density that exists.

Handing this function a smaller tau is not an error and it is not checked for: the reduced variables come out, and a functional built on them returns a number. But that number is not Libxc's. Libxc clamps alpha at zero, so its value stops responding to sigma past the bound; this package carries the negative alpha through. Measured on mgga_c_rregtm at rho = 0.01, tau = 0.3 rho (2026-10-08): the two agree exactly while tau - tau_W = +3.6e-5 and part company at -1.4e-4, where Libxc freezes at -0.0157741004 and this package goes on to -0.0033.

So a disagreement with Libxc found below that bound is a statement about an input no density produces, not about either implementation. For the inputs a test or a benchmark uses, sigma = c_s * rho with tau = c_t * rho is physical only for rho >= c_s / (8 * c_t): the common choice sigma = 0.1 rho, tau = 0.3 rho needs rho >= 0.0417.

Below it nothing is reported: mgga_x_scan returns -0.8674 at tau = 0 and -0.8702 at tau = -0.1, both finite (2026-10-08).

This bound is of a different kind from sigma >= 0. There, one argument is outside the range its own quantity has. Here every argument is a value its quantity can take, and it is the combination that no density produces, so nothing in the arguments is checkable one at a time, and the caller is the only place that knows whether its tau and sigma came from the same density. Hence the inequality, written out, rather than a check.

The reduced Laplacian has no bound of this kind: lapl may take either sign, and does.

8. Potential-only entry points

Seven identifiers for which Libxc reports no energy at all. They return a potential directly, so they have no zk, and the derivative functions in group 2 refuse them by name rather than returning a meaningless number.

There are eight entry points for those seven identifiers. The eighth, mgga_x_2d_prp10_vxc, is one of the 35 kernels Libxc does not register under a name of its own: the only registered functional built on it is mgga_x_2d_prhg07_prp10. It is callable here, and there is nothing in Libxc to compare it against on its own, which the test suite asserts by name rather than skipping.

LibXcDerivative.lda_xc_tih_vxc — Function
lda_xc_tih_vxc(rho)

The exchange-correlation POTENTIAL, not an energy density.

Libxc files this functional under one of its *_vxc families, where the maple source is the potential itself: the C carries #define XC_NO_EXC, and the library reports no XC_FLAGS_HAVE_EXC for it. There is no energy here to differentiate, and this potential is not the functional derivative of one. The functionals Libxc files this way – LB94, BJ06, TB09, RPP09 and this one – were put forward as potentials to begin with, which is why Libxc generates them apart from the energies.

So the contract the rest of this package keeps does not hold for this name. Everywhere else a name returns an energy density and the caller differentiates it to get a potential; here the potential is what comes back, and differentiating it gives Libxc's next derivative order.

Checked against the library Libxc.jl vendors for the value and its first derivative, which is as far as that library goes. Only vrho is non-zero – Libxc returns exactly 0 for vsigma, vlapl and vtau here – so there is no counterpart to those and none is offered.

Spin-resolved arguments are not taken: a potential has one component per spin channel, and this kernel returns a single scalar.

9. Connections to other packages

LibXcDerivative.dft_functional — Function
dft_functional(name) -> DftFunctionals.Functional

Wrap the functional name in the interface DftFunctionals.jl defines.

That interface is what DFTK.jl consumes: family, kind, identifier, parameters, change_parameters, needs_σ, needs_τ, needs_Δρ, has_energy, and the array-based energy_density, potential_terms and kernel_terms.

Available once DftFunctionals and ComponentArrays are both loaded; the implementation is an extension, so neither is a dependency of this package.

How far the array-based evaluation reaches is split between the two packages. DftFunctionals itself implements energy_density, potential_terms and kernel_terms for Functional{:lda} and Functional{:gga} only. This extension adds potential_terms and energy_density for Functional{:mgga} and Functional{:mggal}, built on xc_exc_vxc, so a meta-GGA has those two here as well as a scalar energy.

kernel_terms is deliberately absent for the meta-GGA families: DFTK, which is what consumes this interface, says it does not need one. xc_fxc answers for a meta-GGA's second derivatives in this package's own form.

A potential-only functional is constructed and reports has_energy false. Evaluating one through the interface is not implemented: the generic paths assert an energy, and what those functionals return is a potential.

Deliberately not DftFunctionals.DftFunctional(::Val{name}). That function belongs to DftFunctionals, and a generic method on it here would take effect for the whole process: loading this package would silently change which implementation answers for every identifier DftFunctionals does not define specifically, including inside code that never asked, and the two implementations need not agree to the last digit, since one is written from the papers and the other generated from Libxc. A caller who wants that wiring can write it where it is visible and theirs:

DftFunctionals.DftFunctional(::Val{S}) where {S} =
    LibXcDerivative.dft_functional(S)
source

dft_functional wraps an entry point in the interface DftFunctionals.jl defines, which is what DFTK.jl consumes, including the spin-resolved evaluation that interface's own generic path declines. The extension also provides potential_terms and energy_density for the meta-GGA families.

Everything in this package that differentiates, or that speaks another package's interface, lives in an extension. Loading the package alone leaves those names defined with zero methods, so calling one raises a MethodError rather than anything that mentions an extension.
